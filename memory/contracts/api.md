# API contract — DRAFT — backend owns from M2

Status: drafted by the architect (T-014, round 2). From M2 the backend worker is the sole writer; changes after that go through a card. Frontend may start against the examples below. They use the Appendix A sample case (Jordan Rivera, SYNTHETIC) as stored in `evals/golden/sample.txt`; **every `start`/`end` is an absolute character offset into the case's raw text, and `raw_text[start:end]` equals the quoted string** (verified by a script run for the T-014 handoff). Design rationale: `memory/DECISIONS.md` ADR-002, 005, 006, 007, 009 to 017. Orchestrator decisions: `memory/ORCHESTRATOR_DECISIONS.md` (D-001..D-024). Requirements: `spec/REQUIREMENTS.md`; the conflicts it lists in §8 are resolved in ADR-017.

## Conventions
- Base path `/api`; JSON in and out; UTF-8; ISO dates `YYYY-MM-DD`; timestamps ISO-8601 UTC. Money is integer cents in `value_cents` plus the verbatim `text`.
- `{token}` is the case id: a random 128-bit URL-safe string. It is the only credential. **There is no case-list endpoint.** An unknown token is `404 not_found`.
- Item ids: entries `e…`, amounts `a…`, flags `f…`, records `r…`. Gap flags use `f_gap_<recA>_<recB>`. Opaque to the frontend.
- Errors: HTTP status plus `{"error": {"code": "snake_case", "message": "plain sentence", "detail": {}}}`. Codes: `bad_request` (400), `not_found` (404), `input_too_large` (413), `demo_mode_unsupported_input` (409), `run_in_progress` (409), `needs_confirm` (409, re-run of a case that already has decisions only; never an edit or manual entry, D-047), `item_rejected` (409), `unsupported_language` (400, T-085: see Spanish-language records), `invalid_edit` (422, every structurally invalid edit), `date_invalid` (422, `confirm_date` with a non-candidate date), `llm_unavailable` (503), `busy` (429, retry later; `detail.reason` says which: `pdf_busy` (T-087: more than two PDF uploads are being read at once), `demo_full` (T-183 r2: the public demo already stores `DEMO_MAX_CASES` cases, default 200; on `POST /api/cases`; message "This demo is full right now. Try again later.") or `demo_busy` (T-183 r2: the public demo already has `DEMO_MAX_RUNS` runs in flight, default 4; on `POST /api/cases/{token}/run`, before the case is touched; message "This demo is busy right now. Try again in a minute."). The two demo caps apply only when `ZLAYT_MODE` is not `local`; local/dev is unlimited. A non-integer or non-positive env value falls back to the default. The body is the standard error shape: a plain sentence, no trace, no key, no count).
- Every item has `state` (system: `verified` | `needs_review` | `rejected`), `reasons[]` (codes), `why` (one template sentence), `review_status` (human: `pending` | `accepted` | `edited` | `dismissed`), and `ladder` (D.4).
- `warnings[]` appears on case, ingest, review and export responses. Shape: `{"code": "...", "message": "...", "item_id": null}`.
- Untrusted strings (record text, excerpts, summaries) are plain text; clients must insert them with `textContent`.

## GET /api/health
```json
{ "ok": true, "version": "0.1.0", "synthetic_only": true,
  "banner": "Synthetic data only — never paste real records",
  "backend": "fixture", "demo_mode": true, "local_mode": false, "answers": "prepared", "live_enabled": false,
  "models": {"generator": "claude-sonnet-5-5", "judge": "claude-haiku-5-5"},
  "limits": {"max_chars": 60000, "max_records": 40},
  "retention_hours": 24,
  "ai_banner": "Summaries and flags are drafted by AI and checked by code; you decide every item",
  "sample_available": true }
```
`local_mode` (T-197, additive): `true` only on the private local server (`ZLAYT_MODE=local`, same value that gates `GET /api/cases` and `GET /api/library`, which do not exist in public mode, D-008). The guided UI reads it on first paint and never probes those routes when it is `false`, so a public server sees no 404.

`answers` (T-177, D-065): whose answers the app shows. `prepared` = the curated fixture set (`FIXTURE_SET=curated`): hand-checked by the team, NOT model output; `recorded` = a replay of real model answers (the default fixture dir); `live` = a model answering now. The UI badge follows it: `prepared` -> "Demo: sample answers prepared by our team" (tooltip "Prepared by our team for this demo, not written by an AI model. A second AI model then checked each answer against its quote."; T-177 r2: the report does not hold the answers, so the old pointer was cut), `recorded` -> "Demo: recorded AI answers". With `prepared`, `ai_banner` reads "In this demo the sample summaries and flags were prepared by our team, then checked by code and by a second AI model; you decide every item".

`models` (T-177 r2, D-065) on `GET /health`, `GET /cases/{token}` and `GET /cases/{token}/judges`: `{generator, judge, generator_prepared}`. When every generator answer of the case is a hand-checked fixture (`/health`: the set is `prepared`), `generator` is `"hand-checked (qa)"` and `generator_prepared` is `true`: no model drafted it, so no payload names one as the drafter. `judge` stays the real checking model. Recorded and live cases keep the configured generator model and `generator_prepared: false`. `GET /export` `provenance` carries the same `generator_model` and `generator_prepared`. The UI "How the AI was checked" line then reads "Prepared by our team (not by an AI model), checked by <judge>".
`backend`: `claude-cli` | `anthropic-api` | `fixture`. `demo_mode: true` (the public build) means only recorded cases can be created or run (ADR-006); the UI shows a "cached demo" badge. `live_enabled` is true only when `ENABLE_LIVE=1` and a key exist (local use). The UI shows `banner` on every view and `ai_banner` on the review view; in live mode it also shows "Pasted text is deleted after `retention_hours` hours" with a Delete now button.

## POST /api/cases
Request: `text` (pasted or file contents; `.txt` only, client-side read) **or** `sample: true`. Optional `title` (T-157: the case's name, as typed; `name` is still accepted as the same thing, and `title` wins when both are sent; `POST /api/cases/pdf` takes a `title` query parameter beside `name`). A title is plain text (T-157 r2): control, zero-width and bidi-override characters are removed, line breaks and tabs become spaces, runs of white space collapse; blank means no name. A `title` with a `<` or `>` in it, or longer than 120 characters, is refused: `422 invalid_title` with a plain `message` that never repeats the text, and no case is created (the same for the `title` query of `POST /api/cases/pdf`, checked before the PDF is read). The older `name` field is held to the markup rule too, but a `name` longer than 120 characters (a long file name) is cut, not refused. The response carries `title` (what to show; see "Case titles" under `GET /api/cases`).
```json
{ "name": "Rivera sample", "text": "SYNTHETIC — ...\n\n=== Record 1 ===\nDate: 2026-01-09\nSource: Austin EMS run report\nExcerpt: \"41M restrained driver, ...\"\n...", "sample": false }
```
Request text is normalised first (CRLF and CR become LF; leading/trailing whitespace trimmed). **In demo mode the text is accepted only if its sha256 is in the recorded set (the sample and the golden cases); otherwise `409 demo_mode_unsupported_input` is returned before anything is stored** (D-020). Response 201 (all code: records, dates, duplicates, amounts, gap flags exist before any model call):
```json
{ "token": "k3Jf9xQ2mP7vLw0aZ8tYhA", "name": "Rivera sample", "status": "ingested", "source": "paste",
  "demo_mode": true, "record_count": 9, "split_method": "code",
  "records": [
    { "id": "r1", "seq": 1, "source_label": "Austin EMS run report", "date_raw": "2026-01-09", "date_iso": "2026-01-09",
      "date_status": "parsed", "date_candidates": [], "duplicate_of": null, "injection_tag": false, "encounter": true, "unsplit": false, "preamble": false,
      "char_start": 106, "char_end": 313,
      "text": "=== Record 1 ===\nDate: 2026-01-09\nSource: Austin EMS run report\nExcerpt: \"41M restrained driver, rear-ended at approx. 35 mph. C/O neck pain 7/10 and headache. Alert and oriented. Transported to Central ER.\"" } ],
  "dates_to_confirm": [],
  "gap_flags": ["f_gap_r6_r7"], "record_warning_flags": [],
  "warnings": [] }
```
(The real response lists all 9 records; the example shows one.) `warnings[]` codes: `SPLIT_AMBIGUOUS`, `LLM_SPLIT` (D-031: the code split found one unsplit block, the model proposed record boundaries as character offsets, code validated that they cover the text exactly and start on line starts; `split_method` is then `"llm"`; an invalid proposal keeps one record and `SPLIT_AMBIGUOUS`), `SPLIT_REJECTED` (always follows `SPLIT_AMBIGUOUS` when a reason exists; the reason is `split_failure` on the run result: `NO_MODEL` no model or recorded answer, `NOT_ATTEMPTED` several records plus an unsplit tail so the model is not asked, or `LLM_FAILED_AFTER_RETRIES` / `SCHEMA_INVALID` / `SPLIT_*` from a failed or refused proposal; `split_detail` carries `FIXTURE_MISS`), `UNSPLIT_TEXT` (text outside any recognised record is kept, D-027, as a record with `unsplit: true`; T-129: unsplit records are numbered AFTER the real records so a preamble never shifts "record 1"; the one above the first real record also has `preamble: true`. **Both fields are on every record of `POST /api/cases` and `GET /api/cases/{token}`** (`false` for a real record); the `UNSPLIT_TEXT` warning is in the POST response only. A re-run after a record number came to name different text resets the paralegal's decisions on items that cite it to `pending` (the review event keeps what they were) and removes the stale items), `DATE_EXCLUDED_FROM_GAPS`, `PHI_PATTERN` (SSN/phone/MRN-shaped text found; does not block), `DUPLICATE_MERGED`. Errors: `413 input_too_large`, `400 bad_request` (empty or `.pdf`), `409 demo_mode_unsupported_input` (demo mode, text not recorded).

## POST /api/cases/pdf (D-031)
Request: the raw PDF bytes with `Content-Type: application/pdf`; optional query `name`. Text layer only (pure-python extractor, no OCR); at most 5 MB and 100 pages. The extracted text becomes the case text (pages joined by a blank line), so everything after this is identical to a pasted case, and the demo gate (`409 demo_mode_unsupported_input`) applies to the extracted text. Response 201: same body as `POST /api/cases` with `source: "paste"`, and every record carries `page` (the page where it starts). `GET /api/cases/{token}` records carry `page` too, and export citations read `Source [Ex. __ / Bates __], p. N: "..."` for PDF cases only (unchanged for pasted text).
Errors: `400 bad_request` with `detail.reason` = `pdf_no_text_layer` (looks scanned: refused before anything is stored, no model call), `pdf_unreadable`, `pdf_encrypted`; `413 input_too_large` (`pdf_too_large`).

### PDF hidden text and local OCR (T-087, T-086; D-042)
Query on `POST /api/cases/pdf`: `include_hidden` = `all` or a page list such as `2,5` (pages whose hidden text the paralegal confirmed; default none) and `ocr=true` (read scanned pages with local Tesseract; default off). Both are decided by re-posting the same file, which creates a new case (ingest is code only, so it costs no model call). Limits: OCR reads at most 10 scanned pages per upload, 150 s in all, nothing leaves the server. A page larger than 40 inches on a side is refused (`ocr_page_too_large`, `detail.page`); a larger one under that is rendered smaller than 150 dpi (longest side at most 3500 px, area at most 8 million px); all page images of one upload together are capped at 12 MB (`ocr_images_too_large`). Tesseract runs with a scrubbed environment (no API key or token reaches it). One deadline (10 s, or 165 s with OCR) covers text reading, the hidden-text scan and OCR; when it passes the work stops and the response is `400 bad_request` with `detail.reason: "pdf_timeout"`.

**Hidden text.** Every text object is checked against the page as rendered (pypdfium2). Reasons: `invisible_render_mode`, `transparent`, `off_page`, `tiny_font` (under 5 pt effective), `blends_with_background` (a differential render, contrast under 96 levels counts as blending: the page is drawn with and without all text, and the text counts as hidden when the two agree under its box, so white or background-coloured text, text under a cover of any pattern, and text with marks, rules or dots in its box are all caught), `could_not_verify` (the check could not be made exactly, so the text is held back as suspected) `covered_by_annotation` (a form field, stamp or other annotation with an appearance lies over the text; some viewers draw it opaque while the renderer does not), `clipped` (a clipping window shows under half of the text's box) and `not_in_rendered_page` (words in the file's text layer that the renderer did not place on the page, for example text nested deeper than the 40 form levels a page draws). Hidden and suspected text is removed from the case text, so it can never ground a quote, until its page is confirmed. **Fail closed:** a page whose check could not run (the renderer cannot open the file or the page, more than 20000 text objects, or more than 400 hidden pieces, or more than 500 annotations) is `unchecked`: its text is kept out of the case and the page is listed in the report with `unchecked: true`, `count: 0` and a plain `why`, until the paralegal confirms the page with `include_hidden`. Both PDF parsers, the text-layer read (pypdf) and the render scan (PDFium), run in one child process that is killed at the request deadline (HTTP 400 `pdf_timeout`; no work survives it, and no PDF is parsed in the API process). The child has a CPU limit, an address-space limit where the OS enforces one (Linux; macOS refuses it, unverified on Linux here) and a parent-side check of its resident memory every 0.1 s that kills it above 1 GiB on every platform (the pages are then `unchecked`). At most two PDF uploads are processed at once; a third gets `429 busy`. A Popup annotation with an appearance over text counts as a cover (`covered_by_annotation`); one without an appearance does not. A file whose only usable text is hidden or unchecked is refused with `detail.reason: "pdf_only_hidden_text"`, `detail.hidden_text_pages` and `detail.unchecked_pages`.
**OCR.** A page with no text left and a picture on it is "scanned". Without `ocr=true` the upload is refused as before (`pdf_no_text_layer`) with `detail.scanned_pages: [..]` and `detail.ocr` (the status object below) so the UI can offer "Read scanned pages (OCR)". With `ocr=true`: `400 ocr_unavailable` (Tesseract missing or too old; `message` is the plain install line, `detail.ocr` the status), `ocr_too_many_pages`, `ocr_failed`, `ocr_check_failed` (the hidden-text check's child process was killed or crashed on this file, so it is not read with OCR; `detail.cause` is `memory`, `child_failed` or `child_died`) and `ocr_render_failed` (the child that draws the pages for OCR was killed or crashed, e.g. ran out of memory). Page drawing for OCR runs in the same killed child process as the hidden-text scan (deadline, CPU and memory limits); the API process never opens the PDF and never retries a failed child itself (T-107). OCR text is quoted exactly as OCR read it.

Response and `GET /api/cases/{token}` gain, for PDF cases only:
```json
"pdf_checks": {
  "hidden_text": {"checked": true, "excluded_until_confirmed": true,
    "pages": [{"page": 2, "count": 1, "excluded": true, "confirmed": false,
               "items": [{"text": "…", "truncated": false, "reasons": ["blends_with_background"], "why": "not visible when the page is shown (the same colour as the page behind it, or covered)"}]},
              {"page": 3, "count": 0, "items": [], "unchecked": true, "why": "The page renderer could not read this page, so hidden text could not be checked.", "excluded": true, "confirmed": false}],
    "unchecked_pages": [3]},
  "ocr": {"requested": true, "ran": true, "scanned_pages": [3], "pages": [3], "engine": "tesseract 5.5.2", "low_conf_words": 12, "items_need_review": true,
          "low_conf_rule": "words under 60 confidence, or under 80 when the word has a digit",
          "status": {"available": true, "version": "5.5.2", "tested_version": "5.5.2", "languages": ["eng"], "message": "Tesseract 5.5.2 is available."}}},
"pdf_pages": [{"page": 3, "start": 0, "end": 812, "source": "ocr", "has_image": true, "mean_conf": 91.2, "words": 120, "low_conf_count": 12,
               "low_conf": [{"start": 40, "end": 47, "text": "Chaege:", "conf": 38.0}]}]
```
`checked: false` means at least one page could not be checked (`unchecked_pages`); those pages are held back like hidden text, so show them as pages to confirm, not as skipped. `pdf_pages[].start/end/low_conf[].start/end` are offsets into the case text; a page confirmed for hidden text carries `hidden_text_included: true`. Every record in a PDF case has `ocr_derived: true|false`.
**Items.** Every non-rejected entry, amount and flag whose record lies on an OCR page is `needs_review` with reason `OCR_DERIVED` (appendix), added by code after the model steps; no judge answer, edit, manual entry, not-a-duplicate split, reclassify, date confirmation or rejudge clears it (an edit of an OCR item stays `needs_review` with `OCR_DERIVED`, because the edit does not show that the page image was compared). Its trace gains a failing code step `ocr_source` ("Record was not read from a scanned page", rule D-042, next action `READ_RECORD`); nothing else about other items' traces changes.
**`GET /api/cases/{token}/pages/{n}/image`** -> `image/png` (greyscale, 150 dpi) of an OCR'd page, stored with the case and deleted with it; `404 not_found` for a page that has none. The UI shows it beside the page's text.

## POST /api/cases/{token}/review/batch (D-031)
**D-051:** accept also refuses (all or nothing) any entry whose current summary fails a code check: `422 CODE_CHECK_FAILED`, message = the plain reason + "Nothing was changed.", `detail.rejected` has `{id, reason: "code_check_failed", reason_code, why, next_action: {code: "EDIT_SUMMARY" | "EDIT_QUOTE", text, target: {item_id}}}`.
Request: `{"action": "accept" | "reset", "item_ids": ["e1", "e2"]}` (1 to 200 distinct ids). **Entries only.** `accept` needs every id to be an entry with `state: "verified"` and `review_status: "pending"`; `reset` (the undo) needs entries only. Amounts, flags, needs_review and rejected items are never accepted in bulk. **D-059 (T-140 r2): charges are never batched.** A batch (accept or reset) that includes any amount of kind `charge` is refused whole: `422 CHARGES_NOT_BATCHED`, message "Charges are accepted one at a time, so a charge cannot be part of a batch. Take the charge out and review it by itself; nothing was changed.", `detail.rejected` lists `{id, reason: "charge_in_batch"}` for each charge. Frontend: remove charges from every batch/"accept all" selection and from any select-all; a charge has only the single-item accept/dismiss. ## /api/cases/{token}/export_config (D-031)
`GET` returns `{"exhibit": null|string, "bates_prefix": null|string, "bates_start": null|int}`. `PUT` takes the same keys (all optional; omitted or empty means unset) and returns the stored config; `DELETE` clears it and returns the empty config. The deadline path adds no note (nothing was redone) and keeps `run_deadline`. A re-run (the case already had entries) where a step failed and there was no earlier result to keep also reads `failed` / `run_partial`: "The AI step failed for N items (writing the entries) on this run, and there is no earlier result to keep. Run it again to retry." **T-161 / T-165, first run:** a first run with a failing step (a second check, the flag step, or the extract step on ANY record) stores its failure stubs and reads `failed` / `run_partial` too, and the export gate lists `RUN_FAILED`. ## POST /api/cases/{token}/records/{rid}/confirm_date
Resolves a record whose `date_status` is `ambiguous` by choosing one of the readings the code proposed (`date_candidates`). It is not an edit (D-010). A record with no readable date (`missing`) cannot be confirmed; it stays excluded and flagged. Request:
```json

```
Response 200: the record with `date_status: "confirmed"`, its entry's date, the **recomputed gap flags** (a changed or new flag keeps no review status; an unchanged record pair keeps its status), the cleared `date_ambiguous` record warning, and `dates_to_confirm`:
```json
{ "record": {"id": "r8", "date_iso": "2026-05-04", "date_status": "confirmed", "date_raw": "04/05/2026"},
  "entry": {"id": "e8", "date": "2026-05-04", "moved_from": "undated_entries"},
  "gap_flags": [],
  "removed_flag_ids": ["f_warn_date_r8"],
  "dates_to_confirm": [], "warnings": [] }
```

It is conservative: a visit word in the label (outside the provider name and parentheses) or treatment evidence in the text means no label. It changes no counted gap date, day count or flag. Confirming record 4 of lib09 as 5 March moves the gap 42 to 40 days and `gap_changes` reports it, as in T-114.
- A gap that starts or ends at record(s) that ALL look administrative has `computed.endpoint_warnings` (always present, `[]` when none) entries `{side: "start"|"end", record_no, record_type, date, warning, alternative, alternative_days, alternative_from, alternative_to}`. `warning` = "This gap ends at record 4: <verbatim header>, which looks like paperwork, not a visit. (several records: "If record 2: A and record 3: B are paperwork, not visits, ..."; `alternative_days`/`_from`/`_to` are the nearest visit dates around the paperwork, `null` and a sentence "there would be no visit before it and no gap to measure." when one side has none). Both sentences are appended to the flag's `explanation`, its `why`, and the item trace. A visit on the same date as the paperwork anchors that end, so no warning. Title and `days` are the COUNTED gap ("Gap of 43 days"); the alternative number is in the sentence.
- **Conditional flag (new).** A span of more than 30 days between two visit dates that paperwork-looking records split into counted pieces of 30 days or fewer is not a counted gap, so it is shown as a gap flag with `computed.conditional: true`, title "Possible gap of 40 days", `from`/`to`/`days` = the visit-to-visit span, `record_nos` including the paperwork record(s) inside, and `endpoint_warnings` entries `side: "inside"` carrying `warning` ("No gap is counted here because record 2: <header> (March 20, 2026) falls inside this span and is counted as a visit (19 days, then 21 days).") and the same `alternative`. `conditional` is absent on counted gaps. The paralegal accepts, edits or dismisses it like any other flag.
- Accident-date conflict: the earliest dated record of ANY kind sets the comparison. If every record on that earliest date looks like paperwork, the explanation never says "first recorded treatment" for it: title "Stated accident date is later than the earliest record"; "... is later than the earliest recorded date, January 12, 2026 (record 1: <header>), which looks like paperwork, not a visit. The records disagree; the tool does not choose between them. If record 1: <header> is paperwork, not a visit, the first recorded visit is January 20, 2026 (record 2: <header>), and the stated date is not later than it. Check when treatment actually began before relying on this comparison." (`also later` when it is; "there is no recorded visit to compare with." when no visit exists). `first_treatment_date` keeps the earliest recorded date. A visit on the earliest date keeps the plain wording.
- Golden `gap_table` rows describe the visit-only reading (what `alternative_*` shows); the product's counted rows can have more rows. Code-built from fixed templates, never model text. (Replaces the T-116 r1/r2 `excluded_records`, removed.)

**T-114: `gap_changes[]`** (always present; `[]` when no gap figure moved). Each element `{flag_id, change: "changed" | "added" | "removed", old_days, new_days, old_from, old_to, new_from, new_to, sentence}`; the side that does not exist is `null`. A gap whose endpoints moved (its id is built from its record numbers) is ONE `changed` element pairing the old and the new gap that share a record. `sentence` is plain words the UI can announce as is, e.g. "Gap recalculated after you confirmed record 4: now 40 days (was 42)." Computed by code from the stored gap figures, never by a model. A gap whose review status was reset by the recompute is exactly the set of `changed`/`added` elements. Each element also has `record_seq` (the record whose date was confirmed). **T-127: the change is kept with the case.** `confirm_date` writes `gap_changes[]` into its `confirm_date` review event (`after.gap_changes`), and `GET /api/cases/{token}` reads it back: a gap flag in `flags[]` whose figures were moved by a confirm_date has `gap_change` (the same element: `{flag_id, change, old_days, new_days, old_from, old_to, new_from, new_to, record_seq, sentence}`), otherwise `gap_change: null`; it stays through reload, another browser and review actions, and goes when that gap's current figures differ from the ones the change produced (a later confirm_date that moves it again replaces it). A gap that no longer applies has no flag, so `GET case` lists it in top-level `gap_changes_removed[]` (same element, `change: "removed"`, `sentence` included) until a gap with the same id exists again. Both are always present (`null` / `[]`). Stored in the DB (the audit event), not in `computed`. `422 date_invalid` when the date is not one of the record's candidates; `422 invalid_edit` when the record's date is not ambiguous. Confirming also removes `DATE_AMBIGUOUS` from the entry's `reasons` and recomputes its `state` (it becomes `verified` unless another reason remains), so the entry reads like any other dated entry and can be reviewed normally. The example is golden `case_01` record 8, a phone note (`encounter: false`): confirming its date moves the entry onto the timeline but changes no gap math, so `gap_flags` is empty. For an encounter record, `gap_flags` lists the recomputed flags.

## Date-convention suggestion (T-088, D-042): `dates_to_confirm[].suggestion`
Every entry of `dates_to_confirm` (in `GET /api/cases/{token}` and in the `confirm_date` response) now has a `suggestion`: `null`, or a hint for an **ambiguous** numeric date. Code only (`app/backend/date_convention.py`). It looks at the other numeric dates in the packet whose order is certain (one number above 12: `03/14/2026` is month first, `14/03/2026` is day first), in each record's date label and text. It suggests only when all of that evidence agrees; no evidence, or evidence in both orders, gives `null`.
```json
{ "record_id": "r8", "raw": "04/05/2026", "candidates": ["2026-04-05", "2026-05-04"], "status": "ambiguous",
  "suggestion": { "convention": "MDY", "label": "MM/DD", "iso": "2026-04-05",
                  "reason": "Another date in this packet uses month first (Record 1: 03/14/2026)",
                  "evidence": [{"record_id": "r3", "raw": "03/14/2026"}], "evidence_count": 1, "auto_applied": false } }
```
`convention` is `MDY` or `DMY`. `iso` is the candidate that reading gives, always one of `candidates`, or `null` when the year is also ambiguous (two-digit year above 40). `reason` is plain words: one date reads "Another date in this packet uses month first (Record 1: 03/14/2026)"; several read "4 other dates in this packet use month first (Record 2: 02/17/2026) and (Record 6: 03-17-26)" (each example names the record the date sits in; the evidence dates come from the packet, never described as "in this record") (at most two examples in `evidence`, the total in `evidence_count`). `auto_applied` is always `false`.

The suggestion changes nothing: the record stays `ambiguous`, its entry stays in `undated_entries`, and Accept stays blocked (D-041, `DATE_UNCONFIRMED`) until the paralegal confirms through `confirm_date`, which still accepts only a code candidate (`422 date_invalid` otherwise). **UI:** pre-select the radio for `suggestion.iso` (when not null), show `reason` under it, keep the confirm button enabled only on an explicit click, and let the paralegal pick the other reading freely. Do not confirm on load.

## POST /api/cases/{token}/items/{item_id}/review
All single-item human decisions. Request body (one of these per call; shown as an array of alternatives):
```json
[
  { "action": "accept" },
  { "action": "accept", "confirm": "likely_duplicate" },
  { "action": "count", "confirm": "separate_charge" },
  { "action": "count", "confirm": "separate_charge", "confirm_flag": "likely_duplicate" },
  { "action": "dismiss", "note": "false positive" },
  { "action": "reset" },
  { "action": "edit", "edits": { "summary": "Discharged from physical therapy after two missed appointments; pain 3/10." } },
  { "action": "edit", "edits": { "excerpt": "Discharged from PT after two missed appointments. Pain 3/10." } },
  { "action": "edit", "edits": { "note": "Ask client about the 2023 episode." } }

```
Allowed `edits` by type (D-010, D-012): **entry** `summary`, or `excerpt` (must be a contiguous run of whole sentences of the same record, so the offsets stay code-derived); **amount** none (accept or dismiss only; its class changes only through `POST .../reclassify`, never through `edit`); **flag** `note` only. Every structurally invalid edit is `422 invalid_edit` (the one code): any other action or key (date, provider, value, kind, flag title or evidence), an edit on a charge, an excerpt that is not a contiguous run of whole sentences of the same record, or one that drops a hedge sentence qualifying a kept sentence. Dates are not edited: ambiguous ones are resolved with `confirm_date`. `edit` implies accept: `review_status` becomes `edited`; the original is kept in `review_events` and shown as "edited" in the review UI and the internal notes. `rejected` items return `409 item_rejected` for accept/edit (dismiss and reset are allowed). Accepting is idempotent. **D-041: accept and edit on an entry without a confirmed date are `422 DATE_UNCONFIRMED` (nothing is saved); resolve it with `confirm_date` first.** The export is defended the same way: an entry with no date is never written into the letter's treatment section (so "date not stated" never appears there) and is listed in the internal notes under RECORDS NOT IN THE TREATMENT SECTION as "date not confirmed, not exported".

**Edit re-check order (R-RV-3, ADR-005; D-034, D-047).** (1) Structure, else 422. (2) Code checks (ADR-012). Any of these is a **hard `422 invalid_edit`**: nothing is saved, no judge call is made, no event is logged, and there is **no confirm or override** (the `409 needs_confirm` / `confirm_warnings` / `keep_my_wording` path is removed; a `confirm_warnings` field in a body is ignored):
- a number, date or $ figure in the summary that is not in the quote, its source label or the parsed date: `detail.reason "SUMMARY_NUMBER_NOT_IN_EXCERPT"`, `detail.tokens`;
- a side or negation word in the summary that the quote does not have (`left`, `right`, `bilateral`, `no`, `not`, `none`, `never`, `without`, `denies`/`denied`, `negative`, `absent`, `neither`, `nor`, and n't forms such as `didn't`), or a qualifier word the quote has no qualifier of that kind for (an attribution such as `patient reports`, `states`, `per patient`; a hedge such as `possibly`, `likely`, `suggests`, `may`; an approximation such as `about`, `approximately`, `~`): `detail.reason "SUMMARY_TOKEN_NOT_IN_EXCERPT"`, `detail.tokens` (the summary's own words). One shared source: `grounding.new_tokens` (side and negation list, `added_qualifier_tokens`), used by the route, the generator and the gate;
- a qualifier the quote carries that the summary leaves out (hedge, attribution phrase, negation, side, approximation): `detail.reason "SUMMARY_DROPS_QUALIFIER"`, `detail.qualifiers[]` (`hedge`, `self_report`, `negation`, `laterality`, `approx`);
- a quote that cannot be located in the record: `detail.reason "HIGHLIGHT_NOT_FOUND"`;
- a dollar amount in the summary or the quote (T-139, D-019, R-CH-7, R-EX-8): `detail.reason "CHARGE_TEXT_IN_ENTRY"`, `detail.amounts[]` (the figures as written). Checked after the number/side/qualifier checks, so a figure that is not in the quote still reports `SUMMARY_NUMBER_NOT_IN_EXCERPT`. See "Dollar amounts in entries" below.
`message` is a plain sentence naming the words, e.g. `The summary says “left”, which the quote does not say. Remove it or change the quote.` The export gate and accept recompute the same checks from the current wording through the same functions (D-051), so an edit the route stores can never be an export blocker for a code reason. The same rule applies to `POST .../records/{rid}/entry`. (3) Judge 1 re-run: it never blocks a human-written edit (D-045b). If it says `partially`/`unsupported`, errors, times out, or has no recorded fixture (always the case in demo mode), the edit is saved, the item becomes `needs_review` (reason `JUDGE_UNAVAILABLE` when it did not answer) and `warnings[]` carries `JUDGE_PARTIAL`, `JUDGE_UNSUPPORTED` or `JUDGE_UNAVAILABLE`; no 409, because nothing the code can verify is wrong. The judge never lets an unchecked edit look verified.

**An edit that is still `needs_review` is not decided (T-134; D-045b, D-051; paralegal pass 4 M2).** Saving the edit stays as above (`review_status: "edited"`, `state: "needs_review"`), but until the paralegal says she compared it with the quote it is **open**, one rule in all places:
- Item view: every entry has `edit_to_check` (bool), true when `review_status` is `edited`, `state` is `needs_review` (any reason: `JUDGE_UNAVAILABLE`, `JUDGE_PARTIAL`, `OCR_DERIVED`, a translation label) and the entry has an edited `summary` or `excerpt`. It is false after accept, dismiss or reset, and for a verified edit. `review.counts.edit_to_check` counts them (they are also still in `counts.edited`). `review.ready_to_export` is false while `edit_to_check` > 0, and an edit still to check does not count as accepted.
- Her explicit **Accept** on it (the UI's "I compared it with the quote") is `{action: "accept"}`: `review_status` becomes `accepted`, `state` stays `needs_review` with its reasons, `edit_to_check` is false. Accept is bound by the code checks (D-051): if the current wording fails any of them, `422 CODE_CHECK_FAILED` and nothing is written.
- Export: the entry is **not in the letter**, not in `items.entries`, not counted in `counts.entries` or `provenance.edited_count`; it counts in `excluded.pending` and in `excluded.edit_not_confirmed` (subset of pending), and in the notes' "Items not reviewed: N". It does not block export (it is not in the letter, as with a pending item, D-045(a)), unless nothing else is accepted (`NOTHING_ACCEPTED`).
- Gate (`/trace` `export_gate`): `warnings[]` gains `{reason_code: "EDIT_NOT_CONFIRMED", count, why, next_action: DECIDE}`; `counts.edit_not_confirmed`; `counts.accepted` leaves it out; the `review` step is `pending` with reason `EDIT_NOT_CONFIRMED`; the verdict label counts it in "Ready to export (N not reviewed)". It is never a `JUDGE_NOT_RUN` blocker while open.
- Internal notes: EDITED ITEMS lists it with "(edited; second check not available (JUDGE_UNAVAILABLE); not yet confirmed against the quote, so it is not in the letter (accept it to put it there))" (the reason sentence follows the item's reasons: `JUDGE_PARTIAL`, `JUDGE_UNSUPPORTED`, ...), PENDING ITEMS NOT INCLUDED lists it with the same phrase, and RECORDS NOT IN THE TREATMENT SECTION says "edited, not yet confirmed against the quote". After she accepts, EDITED ITEMS keeps the reason: "(accepted by the paralegal after comparing it with the quote; second check not available (JUDGE_UNAVAILABLE))". - Item trace (`GET /items/{id}/trace`, the "Why this status" row; T-134 r2): while `edit_to_check` is true the `human` step is `pending` (reason `EDIT_NOT_CONFIRMED`, `blocks_export` false, `next_action` DECIDE) with "You edited this item; it is not accepted until you compare it with the quote and accept it, so it stays out of the letter.", and the item `verdict` is `{code: "edit_to_check", label: "Edited; waiting for your check"}` (new `verdict.code` value; a failing code check still wins: `needs_attention`). ## T-178 (GATE-M3 chaos): interrupted runs, stale tabs, paste text

**Interrupted run (startup recovery).** A run is a thread of the server process. When the process stops (crash, sleep, redeploy) the case would stay `running` for ever. At startup every case still `running` that no thread of this process is running is set to `status: "failed"` with `error: {"code": "run_partial", "interrupted": true, "message": "The run was interrupted before it finished (the app was restarted or stopped). Items that finished and every decision of yours were kept. Run it again to retry."}` and `run_finished_at` set. The same happens on any read of a `running` case that has no live thread and whose run started more than 600 s ago. Nothing item-level is touched: accepted, edited and dismissed items stay exactly as they were, the export gate reads `RUN_FAILED` (next action `CONFIRM_RERUN`), `POST .../run` is allowed again (`409 needs_confirm` while decisions exist, then `confirm_rerun: true`), and the re-run follows the T-146 rules (decided items are kept). Frontend: treat `failed` + `error.interrupted` like any `run_partial`: show `error.message` and the Run again button.

**Stale second tab (`stale_item`).** Every item view (`entries[]`, `amounts[]`, `flags[]`, `GET .../items/{id}` `item`, review responses `item`) now has `version`: a number that changes whenever the item changes. `POST .../items/{item_id}/review` accepts optional `version` (the item's `version` as the client last saw it) and/or `expected_status` (its `review_status` as last seen: `pending|accepted|edited|dismissed`). If either differs from the stored item the write is refused with `409 stale_item`, message **"This item changed in another tab; reload to see it."**, `detail: {item_id, review_status, version}` (the current ones), and nothing is written (no review event). Neither sent = no check (older clients). A repeat of a decision that would leave the item as it already is (accept on an accepted item, dismiss on a dismissed one, reset on a pending one) is let through. Other values: `422 invalid_edit` (`version` not a number, `expected_status` not one of the four). **Frontend must:** send `version` and `expected_status` from the item it is showing with every accept, dismiss, reset, edit and count; on `409 stale_item` show `error.message`, refetch the case (or `GET .../items/{id}`) and replace that item; update the stored `version` from every response that carries an item (batch responses do not carry one: refetch). Frontend does not send these yet (card note on T-178).

**Paste text.** Text is normalised before the empty check and the size limits (`ingest.normalize_text`, used by `POST /api/cases`, the demo-gate hash, the pipeline and PDF page assembly): every Unicode format character (category Cf: zero-width space/joiner/non-joiner, word joiner, BOM, bidi marks and overrides, soft hyphen, tag characters) is removed, and a lone UTF-16 surrogate is replaced by U+FFFD. A paste with nothing else in it is `400 bad_request` "Input is empty." and costs no model call; invisible characters do not count toward the 60,000-character limit; the stored case text is the cleaned text (excerpts and offsets index it). Every string in any JSON request body (titles, edits, notes) gets the same surrogate replacement at the door. No paste returns a 500.

**Amount classes and charge confirms (T-140 + D-059 + D-060; code only).** **D-060 (T-140 r3): a charge is default-deny.** An amount is class `charge` only on an itemized service line: in a provider bill or ledger, a date of service (any date form; not a statement, due or as-of date or the end of a range), a service description (service noun, CPT, HCPCS or revenue code) and the amount on the same line or table row, under the charges column of a table; a coded line (revenue code, CPT, HCPCS) with no date of its own takes the date or period the record states for its services. In a dated encounter record (ED note, imaging report) the record's date is the date of service and the sentence must carry a charge word beside a service, or be the bare "Charge:" under a header that names the service. Everything else is `unclear`, and `internal_notes_text` says why in plain words ("The line states no date of service, so it is not an itemized service line and is not totaled."). Libraries of statement-level wording are no longer needed to keep a total out of the letter; the rules below remain as the specific reasons. The class is decided by code (`amounts.classify`), never by a model or the second check. An amount is class `unclear`, never `charge`, with its reason shown under `AMOUNTS NOT TOTALED` in `internal_notes_text` ("Not totaled ($2,740.00): Total or subtotal line: it repeats the charges listed with it, so it is not totaled."), when: (1) its label (the words just before it in its clause, the words just after it such as "$300 paid", the first cell of its table row, or its column heading) names a total, subtotal, balance, amount due, payment, adjustment, write-off, credit, reversal, void, refund, recoupment, year-to-date or running figure, previous statement or balance forward, or statement-level figure ("New charges"); a table row such as `Total $380 $77 $305` makes every figure on the row a non-charge; (2) it carries a minus sign, parentheses or a CR suffix, or is $0; (3) it comes from an insurer document (EOB, remittance) restating the provider's bill ("Amount billed"). A cue word inside a service description stays a charge ("Chiropractic adjustment charge $65", "Total body MRI charge", "Balance training charge", "Total of 12 visits billed"). A UB-04 `FL47 total charges` line is the column of a revenue-code line and stays a charge; `Rev 0001` is the claim total. Two lines of one record never merge, even at the same price. **D-062 (T-140 fix-up).** The letter's total line reads exactly `Billed charges accepted from these records: $X`; `totals.letter_line` carries the same string. Charge sources: only documents with a billing header (itemized statement, ledger, invoice, UB-04, CMS-1500) yield a `charge`. A record whose header names no provider or kind is unknown and never does ("The record's document type is unknown ..."). ## Check traces (D-042): per-item stepper, case stepper, judge summary
Three read-only GETs that feed the vertical steppers (pattern: <outside project> flow rail: each node has a status, label, detail and note, plus an overall progress count and a verdict). Everything is derived from data already stored (ladder, review status, `llm_calls`, `review_events`, case config); nothing is recomputed by a model. `404 not_found` for an unknown token or item.

**Visibility (same split as `/audit`, D-020/D-036).** Public/demo = **metadata only**. `ZLAYT_MODE=local` = **full**. Both modes return `"mode": "metadata" | "full"`. Metadata mode returns: model id, backend, prompt version and hash, call id, verdict, latency, closed reason codes and their fixed sentences, counts, the item's own excerpt spans and text (the case view already shows them), and the action and time of each human event. **Full mode adds, per step:** `evidence.response_raw` (the model's raw answer for an LLM step), and for the human step `evidence.events[].before/after` and `evidence.edited_text`. **Judge rationale is a closed reason code plus a fixed sentence (D-028).** The judge returns `verdict` + `reason_code` from a closed list, never prose, so `rationale` is the fixed sentence for that code (`why.judge_detail`), written by code. `reason_code` is read from `ladder.judge.reason_code`; for items stored before it was kept (amounts, edits, manual entries) it is read from the audited call's answer.

### Step (shared by all three endpoints)
```json

  "rule": "D-034",                      // decision or LLM_VS_CODE row behind the check, or null
  "blocks_export": false,               // true only for steps that stop this item reaching the letter right now (human pending, date unconfirmed)
  "evidence": { },                      // see below; keys are present only when they apply
  "next_action": null }                 // object when status is "fail" or "pending", else null
```

`status` meaning: `pass` the check ran and passed (or the human decided to accept); `fail` the check ran and found a problem (the item is then `needs_review` or `rejected`); `skipped` not run on purpose (a step before it already rejected the item, no judge applies to code-made items, the judge did not answer, or the human dismissed it) and `why`/`reason_code` say which; `pending` not done yet (the AI run has not reached this step, or the human has not decided).

## POST /api/cases/{token}/rejudge  (D-044)
Run the second check again for the AI-made items whose judge never answered (the items the export gate lists as `JUDGE_NOT_RUN`, plus any live pending ones with no answer: kept on purpose so the `judges` step's RERUN_JUDGE button always has something to do; D-045 note). No body. The same judge (J1 entry, J2 charge, J3 AI conflict, J4 AI flag) gets the same input the run or the edit gave it, so a recorded answer is found again. Same rules as `/run`: `404 not_found`; `409 run_in_progress`; `409 demo_mode_unsupported_input` (demo mode, text not a recorded case); `503 llm_unavailable`. **Demo mode (no `ENABLE_LIVE=1`) is fixture-only**: only recorded answers are replayed, a miss stays unavailable and never calls a model; live calls (`claude-cli` or `anthropic-api` with a key) need `ENABLE_LIVE=1`. Every call is audited in `llm_calls` (judge role, item id, step `j1`..`j4`) and each attempt is appended to the item's `ladder.rejudge[]` `{at, call_id, verdict}`.   "hitl": { "pending": 7, "needs_review": 4, "needs_review_open": 4, "edits_to_check": 0, "could_not_verify": 1,
```
            "gate_blockers": [ { "reason_code", "kind", "item_id", "why" } ], "gate_warnings": [ { "reason_code", "count", "why" } ] },
  "export_ready": true,
  "next_action": { "item_id": "f_r3_1" | null, "kind": "entry|flag|amount|case|run", "reason": "plain sentence" } | null,

```
**`status_error` (T-175 r2).** A case that was deleted while the list was read is left out. A case whose summary fails once is read again after 50 ms (a run or review was writing): if that works it is a normal row. If it fails twice in a row the case exists and the failure is a bug: the row is still listed (one bad case never takes the whole list down) but with `status_error: true` and `status_error_message: "We couldn't load this case's status"`. On such a row `record_count`, `counts`, `progress` and `hitl` are all `null` (never zeros), `export_ready` is `false`, `next_action` is `null`; `token`, `title`, `name`, `source`, `status`, the three times and `run` are still filled from the case row. The frontend shows the message in place of counts and progress, not an empty or zero state. Normal rows carry `status_error: false, status_error_message: null`. The server logs it at ERROR as `case list: a case's status could not be computed twice in a row (<ExceptionClass>)`, never any record text.
**Case titles (T-157).** `title` is what to show and is never "Untitled case": (1) the case name made readable (a file name or slug such as `smith_records-2024.pdf` becomes "Smith records 2024", the `case_lib01_` library prefix is dropped; a typed name keeps its words); (2) when the case has no name, or a name that is empty once cleaned (`case_01_`, `.txt`), the first record header: the provider (its Source line with any tags or angle brackets dropped, at most 60 characters) and that record's date, "Marrowgate General ED, Feb 14, 2026" ("Records from Feb 14, 2026" when the record has no Source line, the bare provider when it has no date); (3) when no record has either, "Records added Nov 2" ("Sample case" for the sample). `name` is the stored value, `null` until someone names the case. `PATCH /api/cases/{token}` with `{"title": "Rivera v. Acme"}` stores the name (same rule as on create: plain text, control characters removed, white space collapsed; a `<` or `>` or more than 120 characters is `422 invalid_title` and the stored name is unchanged) and answers `200 {token, name, title}`; a blank or `null` title clears the name, so the title returns to the derived default; a body without `title`, or a `title` that is neither text nor null, is `400 bad_request`; an unknown token is `404 not_found`. The name goes through the same readable-title step as any other, so underscores or a file extension in a typed title are shown as words. Allowed in public mode too (the token is the capability). A rename is not a review event. **A title is never markup:** a typed title is refused if it contains `<` or `>`, and a title derived from a record's Source line has its tags dropped, so `title` is always plain text and a client may still render it as text only (`textContent`), never as HTML.

**`next_action` (T-157).** The single first thing to do in the case, `{item_id, kind, reason}`, or `null` when nothing blocks the export and nothing waits for review. Code only; no model call; the same value in `GET /api/cases` and `GET /api/cases/{token}`. Order: (1) a case only ingested (not run) is `{item_id: null, kind: "run", reason: "Run the case to draft the timeline. ..."}`; (2) else the first export-gate blocker (`hitl.gate_blockers`, in the gate's order): `kind` and `item_id` are the blocker's (`kind: "case"` and `item_id: null` for a run in progress or failed; `entry|flag|amount` for a code-check failure or an accepted item whose second check never answered) and `reason` is its plain `why`; the `NOTHING_ACCEPTED` blocker, which names no item, yields to step 3 whenever an item waits, because deciding that item is what clears it; (3) else the first needs-review item that is still open (`state: needs_review` and `review_status: pending`, or an edit not yet confirmed), in timeline order: by the date of the record it cites (a flag citing several uses the earliest; undated last), then that record's position in the packet, then entry before flag before amount, then id; `kind` is `entry|flag|amount` and `reason` is the item's own `why`; (4) else `NOTHING_ACCEPTED` as a blocker if that is all that is left; (5) else `null`. Items the review counts leave out (a tray placeholder the paralegal answered, a rule-filtered proposal, a rejected item) are never named. After each decision the field moves to the next item. `tests/unit/test_case_list.py` compares it with GET case for every library case and checks the order rules. `updated_at` is the same value as `GET /api/cases/{token}` (`run_finished_at`, else `created_at`); `last_activity_at` also counts the latest accept/edit/dismiss. `run` is `/status` (`stage`, `progress.done`, `progress.total`). `progress` counts the live items `review.counts` counts (not rejected, no answered tray placeholder, no rule-filtered proposal): `decided` = accepted, edited or dismissed, and a reworded entry still marked Needs review is NOT decided (T-134); `total - decided` over the three kinds = `hitl.pending + hitl.edits_to_check`. `hitl.needs_review` / `edits_to_check` / `pending` are `GET /api/cases/{token}` `review.counts` (`needs_review`, `edit_to_check`, `pending`); `hitl.needs_review_open` (T-157 r3) is the number of items still open in Needs review: `state: needs_review` and (`review_status: pending` or an unconfirmed edit, `edit_to_check`), i.e. exactly the set `next_action` picks from and the items of `GET /api/cases/{token}` that wait for the paralegal; a reworded entry counts, an accepted item that is still `needs_review` does not (so it is at most `needs_review`). `could_not_verify` is the length of that case's `tray`. `gate_blockers` / `gate_warnings` are the `blockers` / `warnings` of the `export_gate` step of `GET /api/cases/{token}/trace` (same `reason_code` and plain `why`; the blockers are exactly what makes `GET .../export` answer 422), and `export_ready` is the gate's `ready`. A case with warnings only (items not reviewed, edits to check) is `export_ready: true`. `tests/unit/test_case_list.py` compares every field with those routes for every library case.
`GET /api/library` -> `{ "cases": [ { "id": "case_01_date_formats", "name": "...", "description": "..." } ] }` (files in `evals/library/`, falling back to `evals/golden/`; format `<id>.txt` + optional `<id>.expected.json` with `name`/`description`).
`POST /api/cases {"library": "<id>"}` (local mode only; `404` otherwise or for an unknown id) creates a case from a library text exactly like a paste. Cases are isolated: ids are unique per case and decisions never cross cases (T-050).

## GET /api/calibration  (T-099, serves T-090 counts to T-096)
Read-only. Serves `evals/reports/calibration.json` (written by `python -m evals.run`), the measured calibration the review screen quotes. It holds aggregate counts, the statements built from them, the source commit, the backend and the sample size. No case token, no record text, so it works in demo mode with no gate. Any other method is `405`.

Always `200` with one envelope:
- `{"status": "ok", "calibration": {...}, "message": null}`. `calibration` has exactly: `schema` (`evals.calibration/1`), `backend` (`fixture` or a live backend name), `case_count` (the sample size: golden cases pooled), `small_sample` (bool), `source_commit`, `generated_at`, `by_state` (`verified` and `needs_review`, each `{matched, total, cases[]}`), `by_type` (`entry`, `amount`, `flag`, each with the two states as `{matched, total, by_case: {case: [m, t]}}`), `not_scored` (`entry`, `amount`, `flag`, `total`) and `sentences` (`overall` and `by_type`, each state a string).
- `{"status": "missing", "calibration": null, "message": "..."}`: no file yet.
- `{"status": "invalid", "calibration": null, "message": "..."}`: the file is not a valid measurement (bad JSON or encoding, wrong schema, a count out of range, totals that do not add up, or a statement that does not quote its own `m/t`). The file's contents are never echoed; the reasons go to the server log.

Rules for the client: render `sentences.overall.verified` and `sentences.overall.needs_review` verbatim (they name the backend and the basis); never compute or show a percentage; hide the line when `calibration` is null. Nothing is invented: no default numbers appear in any state. `calibration` is served by `app/backend/calibration_route.py`; the route is registered in `create_app` and reads one fixed path.

## GET /api/cases/{token}/billing  (T-083, D-042, D-052)
Billing as a **cited line listing**. Code-only analysis of the case's itemized ledgers (table or sentence form), CMS-1500 and UB-04 claim forms, and EOBs (each EOB service row is a line). Computed on read from the records, never stored, **no model call**, available in every state after ingest and in demo mode. It is an internal review view: nothing here reaches the letter or changes `totals`. **No sums and no comparisons of any kind (D-052, applied strictly in T-103 r2 and r4):** no provider totals, no billed/paid/balance sums, no `complete` flag, no running-balance step check, no ledger-versus-EOB check, and no code that asks whether one figure equals, exceeds or differs from another. A printed token is told from another with the same text by its **position** in its record (an offset range), so two equal figures in one excerpt are two entries; the sign of a charge (`detail: reversal`) is read from its printed credit notation, not from its value. The only tests left on numbers are layout (which header a column sits under, whether two offset ranges overlap) and the grounding verifier's substring check. A listing cannot hide a missing line; a sum or a comparison can. The response has exactly `status`, `citation_failures`, `lines`, `unreconciled`, `skipped_records`, `rules`. The only billing total in the product is the case-level charge total of stated charges (D-019, `totals`), unchanged. Unknown token: `404 not_found`.
```json

  "status": "listed",                         // listed | citation_failed | none_found. "listed" says only that something was found; it is not a completeness claim
  "citation_failures": [],                    // [{ref, reason}] from the grounding verifier, which the route always runs; non-empty makes status citation_failed
  "lines": [                                  // every figure the records print, in record order, each with a verbatim excerpt and its source record
    { "id": "b3", "class": "charge",          // charge | adjustment | payment | rate | unclear
      "detail": null,                         // null | "reversal" (a charge printed in credit notation, or VOID) | "balance_only" | "eob" (an EOB service row) | see the extra-line details below
      "provider": "Larkspur Hollow Physical Therapy", "record_no": 1, "record_nos": [1], "form": "ledger",    // form: ledger | cms1500 | ub04 | eob
```

**Line classes.** `charge`, `adjustment`, `payment` come from the column or label the figure sits under (a line with several figures takes the first of charge, payment, adjustment); `rate` is a price, never a charge. `unclear` is everything else: a line whose figure could not be read, an **EOB service row** (`detail: eob`; its payer figures are in `eob`, never in `billed`/`paid`), and the **extra lines** (they carry `figure` and `why` instead of the four figure fields), told apart by `detail`: `rate` (class rate), `estimate`, `lien_amount` | `asserted_balance` | `reduction` (LOP and lien amounts, listed apart from the charges), `stated_total_billed` | `stated_total_paid` | `stated_total_adjustment` | `stated_total_balance` (a total the statement prints: UB-04 line 0001, CMS-1500 Item 28 and Item 29, TOTAL CHARGES, BALANCE DUE; listed as printed, compared with nothing), `balance_forward`. **Figure fields on an extra line, `other_figures`, a running `balance`, and everything in `eob` are never summed or compared by a client.** `other_figures` (a list of `{text, cents, usd}`, empty when none) holds every OTHER money token printed on a rate, estimate or LOP/lien row, wherever a parser first put it: the running balance on a price row (a no-cents one such as `$315` keeps its text with `cents: null`), a second amount in an LOP or rate sentence (the first amount is the entry, the later ones are its other figures), a printed balance or total on that row. A token on such a row is never also a line of its own, with no exception: on a UB-04 room row the FL 44 figure is the rate entry and the FL 47 total (and any non-covered figure) is one of that entry's `other_figures` (T-103 r4, T-110 r2). No token is reachable only by reading the excerpt; each text sits inside the excerpt (`verify_citations`: `other_figure_not_in_excerpt`). The class is `unclear` because the code does not decide what such a figure means. A figure that is both an LOP amount and a printed balance is one line.
**Rules (tested).** Figures are whole cents; credit notation (`(70.00)`, `45.00-`, `-45.00`) makes a charge negative (`detail: reversal`) and is read as a reduction in the payment and adjustment columns (magnitude kept). A running balance that does not follow from the line before it is listed as printed, with no flag. Ledger columns are assigned by position under the header (`CHARGES`, `PAYMENTS`, `ADJ`, `BALANCE`); two equally near columns or a figure far from every header is `unclear`, never guessed. `Bal fwd` is not a charge. A repeated line inside one record is listed twice. **Nothing is merged or deduplicated across records or providers (T-103 r3):** two providers printing the same row are two lines, a re-sent statement is two lines (one per record, each citing only its own record, so `record_nos` has one entry), and a line is identified by its record and its position in it (`id` follows record order, then position). Only a byte-identical copy of a whole record is dropped, at ingest (`duplicate_of`). CMS-1500 money boxes have no decimal point: `85 | 00`, `85 00` and `8500` are all $85.00. UB-04: only FL 47 is a charge; the FL 44 figure on a room line is a `rate` and the `0001` line is a printed total. A fee-schedule or per-unit figure is a rate; a table row or a sentence that carries a rate cue (per visit/session/hour/day, each, /visit, x N, daily rate; one shared test, `amounts.has_rate_cue`, also used by reclassify) is a rate even beside the word charge or billed, is listed once, and a `RATE` column's figures are rates too. A ledger-table figure with no cents (`$185`, `185`) under a money column stays on its row as `unclear` text (`LINE_UNCLEAR`); on a rate row it is a `rate` line with `cents: null`, and a no-cents balance on a rate row is that rate's `other_figures` entry. A blank DOS cell stays blank (`dos: null`, `NO_DATE_OF_SERVICE`); the posting date is never read as the service date. A figure with OCR letters, other than two decimals, or inside an injection-tagged record has `cents: null` / the record is in `skipped_records`. A billing-looking record in no known layout is a `skipped_records` entry `UNRECOGNISED_BILLING_FORM`. An EOB service row (date, service code, then one figure per header column: BILLED, DISCOUNT, ALLOWED, DEDUCT, COINS, PLAN PAID, YOU MAY OWE) is a line of form `eob`; it is never compared with the ledger, so a difference in billed or paid is simply two cited lines. A service code and the number in a reason code (`PR-1`, `CO-45`) are not money. Every cited excerpt anywhere in the response (lines, cites, unreconciled) is checked against the record's own text, and every figure text (including each `eob` figure) against its excerpt, by `verify_citations`, which the route runs on every call; failures are returned as `citation_failures` and make the status `citation_failed`.
**Nothing is silently missing (D-049, tested).** After every parser has run, the code reads each billing record again with its own tokenizer and collects every money-shaped token: a `$` figure, a number with two decimals (OCR letters tolerated), and a whole number in an amount position (under a ledger or UB-04 money column, in a prose sentence, in a balance-forward row, in the box of a dateless CMS-1500 service line; dates, times, codes, years and counts of visits/units/days are not tokens, nor is a whole number on a UB-04 revenue-code row that has a decimal figure to its right (the units count), a procedure code pushed into an EOB money column by a money-shaped service slot, or a prose number directly after another money figure; definition in the `app/backend/billing.py` docstring). Each token is a `lines` entry, an `unreconciled` row, an `unclear` figure on its row, or its whole record is in `skipped_records`. A token none of these holds is added to `unreconciled` as a `ROW_NOT_PARSED` row (one already on that row is extended). The test replays every money token of the T-083 probe sets (r1 to r5 reviews, `artifacts/review-evidence/T-083-*`) plus 600 random insertions (seed 20261102) and 5 x 600 more (seeds 1 to 5), and fails if one is missing or if the exact per-record count differs. Repeated summary rows are never overwritten: two balance-forward rows, and a second TOTAL CHARGES / BALANCE DUE / paid / adjustment row (in one record, or in a second statement of the same provider and form family) are all listed (the earlier ones in `unreconciled`, the last as a line; a copy of a statement in a second record lists that record's totals again, one set per record). An EOB money token is a `$` figure with or without cents, a decimal (OCR letters tolerated), or a whole number under one of the EOB money columns; a row whose figures do not map one-to-one to the columns (a `$140`, `1O0.00`, `130.5`, a bare `130`, a missing or extra figure) keeps every token on its row in `unclear`. A printed total on an EOB (its TOTAL row) is an `unreconciled` row of form `eob`. The test also deletes each EOB figure in turn and requires the oracle to name it. A second test counts the money tokens per record (in every probe and in every random draw): the multiset of normalised token texts in the output's figure fields (`billed`, `paid`, `adjustment`, `balance`, `eob`, `unclear`, `figure`, `other_figures`, `unreconciled.figures`; never an excerpt) must equal the multiset in the input, so a token listed twice or listed for another token's sake fails as surely as a lost one.
**Check codes (closed list, fixed message each):** `LINE_UNCLEAR`, `NO_DATE_OF_SERVICE`, `ROW_NOT_PARSED` (the last is the `reason_code` of an `unreconciled` row). None involves arithmetic. Removed by D-052: `LEDGER_TOTAL_MISMATCH`, `LEDGER_BALANCE_MISMATCH`, `CLAIM_TOTAL_MISMATCH`, `CLAIM_LEDGER_BILLED_MISMATCH`, `BALANCE_STEP_MISMATCH`, `LEDGER_EOB_PAID_MISMATCH`, `LEDGER_EOB_BILLED_MISMATCH`, and the response fields `payer_reports`, `providers`, `totals`, `complete`, `balance_convention`, `stated_totals`, `checks`, `line_flags`, `lop_lien`, `excluded`.
**Ladder.** All steps are code (parse, cite); there is no model step, so no judge. The human step is reading the view; none of it is exportable.

## Spanish-language records (T-085, D-042)

Languages: English and Spanish. Code detects the language of every record (`app/backend/language.py`, a stop-word and script scorer; no model). Text with no evidence for any language (numbers, codes) counts as English; anything with some non-English evidence never does (see *Uncertain language*). Short clinical Spanish lines (`RM cervical: protrusión discal C5-C6, posible estenosis foraminal derecha.`) are recognised from clinical vocabulary. Mixed English/Spanish text is supported.

- **Quote.** For a Spanish record the entry `excerpt` is always the original Spanish, checked word for word against the record text (accents included). A model quote that is a translation is `rejected` (`GROUNDING_EXCERPT_NOT_VERBATIM`). Offsets point into the original text.
- **Summary.** English, written by the model with `extract_es_v1`; it is an AI translation. Code checks (D-034/D-022) run across the language gap: numbers (including `$1.250,00` and spelled-out Spanish numbers), months (`14 de mayo de 2026` is May 14; a numeric date is read day first), right/left (`derecho`/`izquierdo`), negations (`no`, `sin`, `niega`, `negativo`, `jamás`, `carece`, `libre de`, `ni`, `nada`; not `sin embargo`/`sin duda`), hedges (`posible`, `podría`, `compatible con`, `sugiere`, `quizás`, `tal vez`, `impresiona`, `eventual`), `no se descarta` (NOT ruled out: the summary must say it cannot be excluded or is possible; "ruled out" fails) against `se descarta` (ruled out: "cannot be excluded" fails), who said it (`refiere`, `manifiesta`, `aqueja`, `alega`, `señala`, `expresa`), approximations (`aprox.`). A failure gives `SUMMARY_TOKEN_NOT_IN_EXCERPT` / `SUMMARY_DROPS_QUALIFIER` and `needs_review`, as for English. Judge 1 runs with its own prompt (`judge_faithfulness_es_v1`, same verdict enum and reason codes).
- **Entry field `translation`** (every entry view; `null` for English records): `{source_language: "es", source_language_name: "Spanish", label: "AI translation", summary_is_translation: true, quote_is_original: true}`. After the paralegal edits the summary, or writes a manual entry, `label` is `"Translation (edited by reviewer)"`. The UI must show `label` next to the summary and show the quote as the original Spanish. Edits and manual entries on a Spanish record are checked against the Spanish quote and judged with the Spanish prompt.
- **Never auto-verified (D-050).** Every item (entry, amount, flag) made from a record routed `es` or `uncertain` is `needs_review` with reason `AI_TRANSLATION` ("AI translation — check against the original"), whatever the Spanish code checks and the translation judge said. Their failures still show in the trace; passing them never yields `verified`. Enforced once, in `confidence.compose_state` (ctx `translated`), and every path that rewrites a state passes it: pipeline, rerun, rejudge, edit and manual entry, date confirmation, reclassify, flags. The entry `translation` block also carries `review_label: "AI translation — check against the original"`. Batch accept refuses such an item (`not_verified`); the paralegal's single accept is the gate and still works, and export needs nothing more than that accept.
- **Record view** has `language`: `"en"` | `"es"` | `"other"` | `"uncertain"`.
- **Uncertain language** (`LANGUAGE_UNCERTAIN`). A record with some non-English evidence but no confident answer (a short line with accents and no clear language; Spanish against French or Portuguese on too little text) is neither run as English nor refused. It goes through the translation path (Spanish prompt, Spanish token checks, translation judge), its `translation` block has `source_language: "uncertain"`, `source_language_name: "an unidentified language"`, and the entry is always `needs_review` with reason `LANGUAGE_UNCERTAIN`. The run warning `LANGUAGE_UNCERTAIN` (`record_no`, `message` with the cause) says so. The English token checks never run for it. French, Portuguese, Italian and German lines of any length that reach two or more distinct words in their own language are `other` (refused as `UNSUPPORTED_LANGUAGE`).
- **Export.** In the letter, a translated entry ends with a bracketed, removable note on its own line under the quote (T-121): `[AI translation of the Spanish original; check before sending]` (or `[Translation of the Spanish original, edited by reviewer; check before sending]`), (in the one-line style, at the end of the entry's line); no line starts with `AI translation:`. The quote is the original Spanish. The AI-drafted treatment paragraph (`/narrative`) is English-only and skips translated entries.
- **Warnings** (in `POST /api/cases` and the run result): `SPANISH_RECORDS` (`record_nos`; says that the pre-existing and causation phrase lists are English only, so Spanish records' flags come from the AI check alone) and `UNSUPPORTED_LANGUAGE` (`record_no`; a record in a mixed packet that looks like another language: not sent to any model, no entry, plus a run `errors[]` item with code `UNSUPPORTED_LANGUAGE`, stage `extract`).
- **Unsupported language, whole case.** If no record is English or Spanish: `POST /api/cases` (and `/pdf`) answers `400 unsupported_language`, `message` "This tool reads English and Spanish records. The text looks like French, which is not supported, so nothing was run. ...", `detail: {languages: ["French"], supported: ["English", "Spanish"]}`; nothing is stored and no model is called. Detected names: French, German, Portuguese, Italian, or a script (Chinese, Japanese, Korean, Cyrillic, Arabic, Hebrew, Devanagari, Thai, Greek).
- **Dates.** A `Date:` header such as `14 de mayo de 2026`, `14-ago-2026` parses (day first, month spelled out, never ambiguous).
- **Not covered:** amounts in Spanish records are classified by the English billing phrases, so a Spanish charge or rate is usually `unclear` and goes to the paralegal (T-084 reclassify); Latin-American `$1.250,00` figures are read as `$1.250` with no value (`unclear`), never as a wrong number.

## Summary clause trimming (T-112, D-054)
Before judge 1, code (`app/backend/summary_trim.py`) splits each AI summary into clauses (`;` `,` sentence-ending `.` and the join ` and `; ` with ` is not a boundary, so `Neck pain consistent with sprain.` is one clause) and removes a clause only when it adds salient content its own quote lacks (T-112 r2): a procedure/treatment/device/drug term, a body part, or a diagnosis noun that the quote (and, for body part, side and imaging modality, the record's source label) does not have, matched by word family (Tylenol~acetaminophen, cervical~neck, fingers~digits). A number, month, side or negation the quote lacks counts only for a clause that shares no content word with the quote. A changed number or side on the quote's own topic stays and is flagged `needs_review` by the D-034/D-047 code checks (which look for the word anywhere in the quote); a negation on the quote's own topic also stays but is only guaranteed to reach judge 1 and the paralegal: if the quote has the same negation word elsewhere (`No cervical strain.` over `X-ray: no acute fracture. Cervical strain.`), the token check does not flag it. Clinical abbreviations are spelled out on both sides before matching (lac, DJD, OA, RA, ESI, TPI, BLE/LLE/RLE/LE, BUE/LUE/RUE/UE, US, IM, C-collar, APAP, CP, ORIF, TKA and similar), so a faithful expansion is not trimmed. A clause with no such content stays even if none of its words appear in the quote ("Dizziness reported." over "Pt dizzy since crash."): judge 1 still checks it. Whole clauses only. Code does not promise that the kept text reads as a finished sentence (a clause is never edited; the judge and the human check the wording); what it does guarantee, with no word list (T-128 r3): code trims only a SUFFIX, so the kept text is always a prefix of whole clauses and a clause is removed only when every clause after it is removed too (nothing kept can depend on something removed; `Shoulder pain; surgery performed; due to torn labrum.` keeps both or drops the tail), the FIRST clause is never removed (an unsupported first clause means nothing is trimmed and the whole summary goes to judge 1; a summary with every clause unsupported still goes to the tray), and the kept prefix has at least 2 content words; when a rule says no, nothing is trimmed; a with-phrase is removed with its head or kept with it (`Neck pain; diagnosed with diabetes.` removes the whole clause `diagnosed with diabetes`; a summary that is one unsupported clause, such as `Neck pain consistent with sprain.` over `Neck pain.`, goes to the could-not-verify tray). Nothing else changes: the model's original output stays in `ladder.generator.output`, and `ladder.summary_trim = {rule, original_summary, removed[], notes[], kept_summary}` records what code removed (`notes[i]` = "removed from the summary: not in the quote: '<clause>'"). The entry's `summary` is the kept text; judge 1 and every later check see it. If every clause is removed (or what is left has no content word), no entry is made: the record gets a could-not-verify tray placeholder with reason `SUMMARY_NOT_IN_QUOTE` (state `rejected`, `ladder.failure`, not an error in `errors[]`). Human-written summaries (edit, manual entry) are never trimmed (D-047 refuses an unsupported one), and neither are summaries of Spanish or uncertain-language records (D-050 makes those needs_review anyway). Frontend: show the `summary_trimmed` trace step when present; a tray item with reason `SUMMARY_NOT_IN_QUOTE` uses the same wording as other placeholders (the `why` sentence names the cause).

## Dollar amounts in entries (T-139, D-019, R-CH-7, R-EX-8)
The extract prompt asks the model for the sentences that carry "the treatment, findings, diagnosis, plan or charge", so an entry's summary or quote can state an amount ("Charge per visit $140", "ED charge: $3,915."). The letter prints a dollar figure only in the BILLED CHARGES section (accepted charges and the R-EX-8 total line). Code only (`app/backend/charge_text.py`), no model:
- **Pipeline.** An entry whose summary or quote states a currency figure (`$` figure incl. OCR-noisy `$1,2OO`, `N dollars`, `USD N`) gets state `needs_review` with reason **`CHARGE_TEXT_IN_ENTRY`** (appendix; `why`: it is held out of the letter; dismiss it, or pick a quote without the amount and edit the summary to match). **T-139 round 2: money written without a `$` counts too** when a money word or claim-form field names it: `TOTAL CHARGE 49100`, `AMOUNT PAID 0 00`, `Charges: 3,915.00`, `Cost estimate 4,500`, `Fee 140/visit`, CMS-1500 `24F 25500` and `CPT 99204, 18500, 1 unit`, UB-04 `FL47 4920 00`, Item 28/29/30. Dates, pain scores, doses, visit counts and CPT/ICD codes are never currency. `detail.amounts[]` then holds the label with its figure as written. It is an ordinary queue item; nothing is rejected.
- **Narrowing first (T-139 follow-up, code only).** Before the hold-out, when the quote has several sentences and its currency-bearing sentence(s) sit at the START or END, code drops them (`charge_text.narrow_excerpt`): the narrowed quote is a contiguous run of whole, verbatim sentences (a substring of the model's quote; an amount in the MIDDLE, a single-sentence quote, a quote that is all amounts, or fewer than 2 content words left means no narrowing). The summary is then trimmed against the narrowed quote (D-054, then the trailing-amount-clause rule above). Every rung-1 check re-runs on the narrowed pair (`generator.verify`); it is kept only if the pair states no amount, some summary is left, and no check raises a reason the original pair did not already raise; otherwise the entry keeps its quote and is held as above. Judge 1 runs on the narrowed pair (D-044/D-058), so no answer given for the longer quote is reused; with no answer the entry is `needs_review` with `JUDGE_UNAVAILABLE` (JUDGE_NOT_RUN). The entry's `quote`/`excerpt` and offsets are the narrowed text. `ladder.excerpt_narrowed = {rule: "T-139", original_excerpt, dropped[], summary_removed[], original_summary}` records what code dropped; `ladder.generator.output` keeps the model's own output. Frontend: when `ladder.excerpt_narrowed` is present, say "charge sentence not quoted" next to the quote; the paralegal can still re-pick a longer quote, but a quote with an amount is refused as above. Over the 25 recorded cases, 51 entries stated an amount; 42 are narrowed (39 verified by judge 1, 3 need review for other reasons) and 9 remain held (single-sentence billing statements).
- **Round 3: more ways to write money (adjuster r2), same hold.** Also counted as currency: another sign or code next to a figure (`\u20ac185`, `185 \u20ac`, `\u00a31,200`, `1.200,00 \u20ac`, full-width `\uff04185`, `EUR 185`, `185.00 EUR`, `CAD`, `MXN`, `GBP`, `AUD`), amounts in words before a currency noun (`one hundred eighty-five dollars`, `a thousand bucks`, `400 pesos`, Spanish `cuatrocientos d\u00f3lares`), more money words with a money-shaped figure (`Total: 1,200.00`, `Amount: 1,200.00`, `Bill 3,915`, `Invoice total 1,567.05`, `Lien amount 4,000`, `Out-of-pocket 1,200.00`, `Self-pay rate 185`, `Network discount`, `Adjustment -1,250.00`, `Medical specials total`, `Saldo`, `Costo`, `Fee 95`), `185 per visit`, and a figure inside a patient's statement (`Patient states the ER bill was 3,915`, `she owes the chiropractor about 2,400`, `charged me fifteen hundred`). Plain clinical number words (`twelve visits`, `two weeks`, `twenty minutes`) and figures with a unit are never money; `type of bill 0111` is not. **Closed world, written down:** not detected are slang or shorthand (`one eighty-five each`, `6.5k`, `x 185`), bare decimals with no money word (`Initial exam 185.00`), per-mile rates, and Spanish number words other than the hundreds, so a record that states money only like that still reaches the carrier letter if the paralegal accepts it; the reviewer reads every quote before accepting. **T-139 round 4 (structural, after the round cap): ONE detector.** All of the above lives in one module, `app/backend/money.py` (`hits`, `strings`, `has_money`, `of_kind`, `dollar_strings`, `lines_with_money`), and `charge_text` (the hold and the edit check), `export` (the gate below) and `evals/letter_check.py` (the audit) all call it; none has a regex of its own, so a wording one holds, all hold (`tests/unit/test_t139_r4.py::test_the_three_callers_use_the_one_detector` blinds the module and all three go blind together). New in round 4 (all `CHARGE_TEXT_IN_ENTRY` at accept and edit time and `MONEY_IN_LETTER` in the gate): labelled figures after a money label with cents, thousands separators or any digits (`Patient responsibility 1,200.00`, `Paid in full 2,150.00`, `Reimbursement 2,150.00`, `Lost wages 1,800.00`, `Wage loss`, `Usual and customary 185.00`, `Dollars: 185.00`, `settlement offer 2,000`, `reduced to 2,000`), a money-shaped figure before bill/invoice/charge (`the 3,915 ER bill`; `charge nurse` is not one), `bill came to 1,380`, `40 a visit` / `185 each visit` with any digit count, number words after a money verb or noun with no currency noun (`billed at two thousand one hundred fifty`, `quoted at fifteen hundred`, `owes twelve hundred`; a lone `one` or a count unit after it is not an amount), the small dollar sign `\ufe69`, `INR`/`CNY`/`PHP`/`BRL`/`Rs.`/`\u20b1`, and Spanish `400.00 por sesi\u00f3n`. Still the closed world above (slang, `x 185`, bare decimals, per-mile rates).
- **Accept (single, batch, and `edit`, D-051 choke point).** Refused `422 CODE_CHECK_FAILED` with `detail = {item_id, reason_code: "CHARGE_TEXT_IN_ENTRY", step_id: "charge_text", failed_steps: ["charge_text"], tokens: [], amounts: [...], next_action: {code: "EDIT_QUOTE" | "EDIT_SUMMARY", text, target}}`; `EDIT_QUOTE` when the quote states the amount (the quote picker), else `EDIT_SUMMARY`. Same shape as the D-051 code checks.
- **Edit.** `edits.excerpt` (the quote picker) with a quote that has no amount: if the summary still states one and the AI wrote that summary (she has not edited it), code removes the trailing clause(s) that state an amount under the D-054 suffix rule (only a run of clauses at the end, never the first clause, the kept prefix keeps at least 2 content words; otherwise nothing is trimmed) and the edit saves with the trimmed summary (`edited.summary`, the original is kept; the internal notes' EDITED ITEMS line shows both). The response `warnings[]` gains `{code: "CHARGE_CLAUSE_REMOVED", item_id, removed: [clause...], message}`. If code cannot trim, the edit is `422 invalid_edit` (`detail.reason "CHARGE_TEXT_IN_ENTRY"`); the paralegal edits the summary. A quote is never rewritten by code.
- **The held-out hint says the true cause (T-139 rounds 3 and 4).** The entry `why` (case view, `GET /items/{id}`), the 422 `message` of accept and of `edit`, and the internal notes' reason all follow one rule (`charge_text.bill_state` over the amount items on the entry's records, not rejected): a record with an accepted charge says "This record is a bill and its charges are already listed under Billed charges, so dismiss this entry unless it states treatment."; a record whose charge is not yet accepted says its charges go under Billed charges once she accepts them; a record whose charge she dismissed says "You dismissed this record's charge, so none of its figures is counted in Billed charges; ..."; **a record whose amounts were read but none is a charge (rates, unclear figures, estimates; 6 of the 11 held entries in the eval corpus) says "Its amounts were read but not totaled (the internal notes say why), so none of them is in Billed charges; dismiss this entry unless it states treatment."**; only a record with no amount at all says "No amount was read from this record, so its figures are not counted in the Billed charges section; the internal notes name them so you can request the bill." When the amount is only in a summary she edited and no amount row of the record carries it (a figure she typed), the message has no bill sentence at all. The static `why` for the code (appendix, trace `state_reasons`) makes no claim about where charges are.
- **Trace (T-139 r3).** Whenever code shortens a quote or strips a summary clause for an amount (narrowing, the trailing-clause trim, the quote-picker edit trim), the item trace carries a code step (`excerpt_narrowed`, `charge_clause_removed`) with the removed text verbatim, the reason, and the before and after quote and summary (see the entry steps in the trace section). The step is internal; the letter and the internal notes carry no trace text.
- **Export gate on the final text (T-139 round 4).** `export.build_export` builds the letter and then scans the FINAL letter text with the one detector: any money expression in the treatment part (everything before the `BILLED CHARGES` section; the section is found by structure, the last `BILLED CHARGES` line before the total line, never by the words in a quote) blocks the export. The accepted-charge lines and the total line are exempt. This catches what no item check saw, including a paralegal's own summary edit stored before a rule existed. An accepted entry whose summary or quote states money is therefore no longer dropped silently from the letter; it blocks. `GET /export` is `422 export_blocked` with `detail.blockers[]` holding one element per offending line: `{item_id (the entry, or null), kind: "entry" | "letter", reason_code: "MONEY_IN_LETTER", line (1-based line of letter_text), text (the line), expressions[] (the money as written), why: "Line N of the letter states an amount (\u2018billed at two thousand one hundred fifty\u2019): \u201c...\u201d. Amounts go only in the Billed charges section, never in a treatment entry.", next_action: {code: "EDIT_SUMMARY" | "EDIT_QUOTE", text, target: {item_id}}}`; `message` is the first `why` plus "The export is blocked." **The trace gate lists it (T-139 r4, D-044/D-045):** `trace.export_blockers` runs `export.money_blockers_for_case` on the case's final letter text (both styles, merged), so the same `MONEY_IN_LETTER` elements appear in `GET /trace` `export_gate.blockers[]` (with `line`, `text`, `expressions`, `item_id` or null with `kind: "case"`), `export_gate.reason_code` is `MONEY_IN_LETTER` when it is the first blocker, `export_gate.counts.money_in_letter` counts them, the case `verdict` is `needs_attention` ("N lines of the letter state an amount"), and `ready` is false exactly when `GET /export` answers 422. Only checked once something is accepted. Old data is unaffected otherwise: the internal notes still list a PENDING held entry under RECORDS NOT IN THE TREATMENT SECTION as "states a dollar amount, not exported (...)" with the same true-cause sentence as the hint (a bill record with an accepted charge: "this record is a bill and its charges are already listed under Billed charges; dismiss this entry unless it states treatment"; a quote that states the amount: "dismiss this entry, or pick a quote that does not state it and change the summary to match in the same edit"; a clean quote with an amount in the summary: "dismiss this entry, or edit the summary to remove it"). `counts.entries` excludes a pending one. A narrative sentence that states money is still dropped.
- **Billed charges section scanned too (T-139 round 5, the last fix; D-063).** `export.letter_money_blockers` also scans the `BILLED CHARGES` section, charge by charge (a header line ends `: $X.XX`; the lines after it, up to the next header, are that charge's quote). A charge line carries its own amount only: on the quote lines the one figure equal to X is allowed; any other money expression (a paid or adjusted figure, patient responsibility, wages, a second charge, number words) and any money in the header (provider, date) is a `MONEY_IN_LETTER` blocker with `kind: "amount"`, `item_id` the charge, `line`, `text`, `expressions`, `why` ("Line N of the letter is a Billed charges line for $X and also states ..."), `next_action` `{code: "DISMISS_OR_ENTER_BY_HAND", target: {item_id}, text}`. Before blocking, code trims: `_amount_quote` removes any other money expression (the one detector, not only `$` figures) from the shown quote by taking a clause of the sentence (between `;` or `,`, cut before a parenthesis, or the line up to the end of the charge's own figure, as in a ledger row `date  service  $150.00  $0.00  $730.00`), still word for word from the record; `Charge: $2,150 (ins paid $1,412.50).` shows `Charge: $2,150`. When no such clause is free of other money (`Insurer paid $1,412.50 of the $2,150 charge.`) the sentence stays and the export is blocked. The trace gate lists the same blockers (`gate.ready == GET /export allowed`), and `evals/letter_check.py` uses the same section rule. **Number words after a money label are money (round 5):** `copay of twenty`, `deductible of five hundred`, `patient responsibility twelve hundred`, `paid in full twenty-one fifty`, `patient spent fifteen hundred out of pocket`, `lost eighteen hundred in wages`, and also with digits `Insurer reimbursed 1,412.50`, `Copayment 40.00`, `Coinsurance 430.00`, `Net due 737.50`, `Med-pay 5,000.00`, `Policy limits 30,000`, `Patient spent 1,500`, `Lost 1,800.00 in wages` (`CHARGE_TEXT_IN_ENTRY` at edit time, `MONEY_IN_LETTER` in the gate). A lone `one`, a count unit (`days`, `weeks`, `visits`) or a label with no figure (`Deductible not met.`, `Paid in full.`) is not money. Still the closed world above (slang, `x 185`, bare decimals).
- **Dismissed charge.** A provider with a dismissed `charge` amount is not listed under BILLS TO REQUEST. **T-139 round 2:** BILLS TO REQUEST lists treating providers and facilities only: a record whose source is a law firm, attorney, payer or EOB, or records custodian (`export._treating`: closed source-word list, or first-person firm wording such as "this firm represents" in the record) is never listed. No dismissed amount is quoted in the letter (the BILLED CHARGES section lists accepted charges only, and an entry quoting the figure is held out as above).
- **Eval.** `python -m evals.letter_check` (also a row and a blocker in `python -m evals.run`): the fixture-backend export of the sample, every golden case and every library packet has 0 currency strings outside BILLED CHARGES, 0 non-accepted amounts inside it, the exact total line, and (all charges dismissed) none anywhere. Round 4: it uses the same `money.py` detector as the hold and the gate, splits the letter by structure (`export.split_letter`), and counts a letter the gate blocks as a violation (`the export gate blocked this letter`).
- **Recommendation (not done, prompt owner):** `app/llm/prompts/extract_v1.md` line 12 should stop asking for the sentence that carries the "charge"; then the models stop quoting amounts and fewer entries are held out. Frontend: show the `charge_text` step reason in the Why text (`why` already carries the plain sentence) and offer the quote picker on a held-out entry.

## Prepared answers (T-177, D-065; amends D-029)
Provenance of every generator answer comes from the fixture's own `recorded_from`. A **curated** fixture (`recorded_from.backend == "curated"`, model `hand-checked (qa)`) is a *prepared answer*, never model output:
- **Item** (`entries[]`, `amounts[]`, `flags[]`, `GET /items/{id}`): `prepared: boolean`. `ladder.generator` carries `prepared` and, when true, `model: "hand-checked (qa)"` (not `claude-sonnet-5-5`). `ai_drafted` keeps its meaning (a person did not write the summary); the UI tag is "Prepared answer" when `prepared`, "AI draft" otherwise.
- **Audit** (`GET /audit` `calls[]`, also `/items/{id}` `calls[]`): each call has `prepared: boolean`; for a prepared call `model` is `hand-checked (qa)` (what is stored in `llm_calls.model`). Judge answers are real recordings (D-056): `prepared: false`, real model id.
- **Trace** (`GET /items/{id}/trace`): `evidence.model.prepared: boolean`, and `evidence.model.id` is `hand-checked (qa)` for a prepared generator step. That step (`extracted`, a flag's `proposed_by_ai`, a narrative sentence's `extracted`) has label "Prepared answer" and `why` "Prepared answer (hand-checked by the team for the demo)". Recorded and live steps keep "AI drafted a summary and picked a quote" / "The AI read this record and proposed a one-line summary and a quote." and the real model id.
- **Case trace** (`GET /trace`, T-177 r2): when every generator answer of the case is prepared (`models.generator_prepared`), the `extract` step is labelled "Prepared summaries and quotes for each record", its `why` says "The prepared answers (hand-checked by the team for the demo) cover all N records.", and `evidence.model` is `{id: "hand-checked (qa)", prepared: true}`; the `judges` step is labelled "Second AI check on every prepared item". Otherwise the AI wording is unchanged.
- **Narrative** (`GET/POST /narrative`): `narrative.prepared` and `narrative.generator.prepared` (model `hand-checked (qa)` when true).
- **T-177 r3 (every sentence, flags, failures, /classic):** a flag whose record's `flags` (or, for a conflict, `conflicts`) call is a curated answer is `prepared: true` too (the ladder records no generator for a flag, so the call is found by the record: item `f_r3_1` -> call item `f_r3`); a phrase-list-only flag counts (the prepared answers did not include it). For a prepared item, every backend sentence that would say an AI drafted, found or proposed it reads "prepared answer(s)" instead: the item's `why` and `explanation`, every trace step `why`, `next_action.text` and `state_reasons[].why`, the judge report's `disagreements[].judge_says`, and the run's `run_partial` / `ENTERED_BY_HAND` messages on the curated set (one table, `why.to_prepared`). The flag steps read "Prepared answer" (found; r4 dropped the "standing in for the AI draft" tail), "Prepared answers did not include this flag" (skipped) and "Phrase list and prepared answers agree". The second AI check is never touched (it is a real model).
